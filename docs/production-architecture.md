# Бизнес-логика и архитектура бота

## Назначение системы

Этот проект представляет собой алгоритмического крипто-бота на `Node.js + NestJS`, который подключается к `Binance` по `WebSocket`, получает рыночные данные, рассчитывает сигналы стратегии и исполняет сделки в режиме `paper trading`, то есть без реальных ордеров на бирже.

Главная задача бота:

- искать торговые возможности на рынке
- входить в `LONG` или `SHORT`
- контролировать риск
- считать финансовый результат
- собирать статистику по торговле
- при необходимости переключаться на более интересный символ

## Основные модули и их роль

### `BotRunnerService`

Это главный координатор бизнес-процесса бота.

Он отвечает за:

- старт торговой сессии
- выбор стартового символа
- запуск цикла сканирования рынка
- прогрев исторических свечей перед началом торговли
- обработку новых свечей
- вызов стратегии
- передачу сигнала в торговый движок
- печать состояния портфеля

Именно здесь реализован основной рабочий цикл бота.

### `BinanceMarketService`

Этот сервис отвечает за рыночные данные.

Что он делает:

- подключается к `Binance WebSocket`
- слушает поток `kline`
- преобразует входящие данные в унифицированную структуру `Candle`
- умеет переподключаться при разрыве соединения
- умеет загружать исторические свечи через REST для прогрева стратегии
- умеет переключать поток на другой торговый символ

### `SymbolScannerService`

Этот сервис отвечает за выбор торгового инструмента.

Он:

- получает доступные символы биржи
- фильтрует только торгуемые пары
- учитывает ограничение по `BOT_ALLOWED_SYMBOLS`
- проверяет минимальную ликвидность
- дополнительно анализирует недавние свечи
- строит score для выбора наиболее интересного символа

Сканер не открывает сделки напрямую. Он только помогает ранжировать рынок.

### `StrategyService`

Это сигнальный движок.

Он:

- хранит историю свечей отдельно для каждого `symbol:interval`
- рассчитывает индикаторы
- фильтрует плохие рыночные условия
- выдаёт одно из решений:
  - `OPEN_LONG`
  - `OPEN_SHORT`
  - `CLOSE_LONG`
  - `CLOSE_SHORT`
  - `REVERSE_TO_LONG`
  - `REVERSE_TO_SHORT`
  - `HOLD`

Ключевая особенность текущей реализации:

- состояние стратегии больше не смешивается между разными парами
- после переключения символа стратегия прогревается на истории именно этого инструмента

### `PaperTraderService`

Это слой исполнения сделок в режиме симуляции.

Он:

- принимает торговое решение
- рассчитывает размер позиции
- удерживает комиссии
- открывает или закрывает позицию
- обновляет стоп-уровни
- поддерживает `trailing stop`
- проверяет `stop loss` и `take profit`
- возвращает результат исполнения или причину отказа

### `PortfolioService`

Это финансовое ядро бота.

Он хранит:

- свободный баланс
- открытую позицию
- реализованный `PnL`
- плавающий `PnL`
- общие комиссии
- количество сделок
- win/loss статистику
- peak equity
- max drawdown
- историю закрытых сделок

## Полный рабочий бизнес-процесс

Ниже описан фактический жизненный цикл бота.

### 1. Запуск приложения

При старте:

- создаётся `NestJS application context`
- поднимается `BotRunnerService`
- при необходимости выбирается стартовый символ через сканер
- загружается историческая выборка свечей
- история передаётся в стратегию для прогрева индикаторов
- открывается `WebSocket` на активный символ

### 2. Получение рыночных данных

Бот получает свечи от Binance.

Для каждой закрытой свечи:

- проверяется, относится ли она к активному символу
- свеча логируется
- эта свеча передаётся в логику проверки стопов и в стратегию

### 3. Проверка защитных условий по позиции

Перед тем как анализировать новый торговый вход, бот сначала проверяет открытую позицию.

Для этого используются:

- `stop loss`
- `take profit`
- `trailing stop`

Проверка идёт не только по `close`, а по экстремумам свечи:

- для long важны `low` и `high`
- для short важны `high` и `low`

Это приближает paper trading к более реалистичной модели исполнения.

### 4. Формирование сигнала стратегии

Если позиция не выбита по защитным уровням, `StrategyService` рассчитывает:

- `EMA fast`
- `EMA slow`
- `RSI`
- `ATR`
- относительную силу тренда

После этого стратегия применяет фильтры:

- индикаторы должны быть прогреты
- волатильность не должна быть слишком низкой
- волатильность не должна быть слишком высокой
- сила тренда должна быть достаточной
- после закрытия позиции должен пройти `cooldown`

Только если фильтры пройдены, стратегия отдаёт торговый сигнал.

### 5. Исполнение сделки

Если стратегия дала сигнал на вход или выход:

- `PaperTraderService` проверяет корректность действия
- рассчитывает размер позиции на основе риска
- удерживает комиссию входа
- создаёт позицию
- при закрытии считает итоговый `PnL`
- удерживает комиссию выхода
- возвращает деньги в баланс

Если сделка не может быть исполнена, сервис возвращает `REJECTED`, а не делает вид, что активность состоялась.

### 6. Обновление портфеля и статистики

После исполнения:

- обновляется баланс
- обновляется реализованный `PnL`
- обновляется накопленная комиссия
- фиксируется win/loss
- пересчитывается equity
- пересчитывается просадка

Это делает метрики бота более честными и пригодными для оценки.

### 7. Выбор более интересного символа

Если позиции нет и рынок по текущей паре выглядит слабым:

- сканер периодически пересчитывает рейтинг символов
- если найден более сильный инструмент
- и число свечей без сделки превышает порог
- бот переключается на новый символ

Перед переключением:

- загружается история по новому символу
- стратегия прогревается данными этого символа
- только потом переключается `WebSocket`

Это устраняет одну из самых опасных ошибок старой архитектуры, когда индикаторы могли считаться на смешанной истории разных инструментов.

## Текущая торговая логика

Сейчас стратегия ближе к trend-following intraday подходу.

Основные идеи:

- торговать только при наличии направленного импульса
- не входить в слишком шумный или слишком мёртвый рынок
- не открывать сделку сразу после выхода, чтобы снизить переторговку
- сопровождать позицию стопами и trailing stop

### Условия long

Long рассматривается, когда:

- быстрая EMA выше медленной
- RSI подтверждает восходящий импульс
- волатильность в допустимом диапазоне
- тренд достаточно сильный
- cooldown завершён

### Условия short

Short рассматривается, когда:

- быстрая EMA ниже медленной
- RSI подтверждает нисходящий импульс
- волатильность в допустимом диапазоне
- тренд достаточно сильный
- cooldown завершён

### Выход из позиции

Позиция закрывается при одном из событий:

- сработал `stop loss`
- сработал `take profit`
- сработал `trailing stop`
- структура рынка сменилась
- стратегия отдала сигнал на выход или переворот

## Управление риском

В текущей версии уже добавлены базовые элементы risk management:

- ограничение размера позиции
- риск-на-сделку через `BOT_RISK_PER_TRADE_PCT`
- `stop loss`
- `take profit`
- `trailing stop`
- `cooldown`
- расчёт `max drawdown`

Это хороший шаг вперёд, но до полноценного production risk engine ещё есть дистанция.

## Что стало лучше после рефактора

Ключевые улучшения:

- исправлен расчёт `equity` при открытой позиции
- выровнен учёт long и short позиций
- стратегия больше не смешивает разные символы в одной истории
- scanner стал ближе к intraday-логике, а не только к 24-часовому движению
- появились более качественные фильтры перед входом
- execution теперь различает исполненную и отклонённую сделку
- логи стали намного понятнее для ручного мониторинга

## Какие логи теперь пишет бот

Бот пишет лог-блоки на русском языке для событий:

- `СВЕЧА`
- `СИГНАЛ`
- `СДЕЛКА`
- `ПОРТФЕЛЬ`
- `ИНФО`
- `ОШИБКА`

Новый формат логов:

- показывает timestamp
- печатает аккуратный многострочный блок
- читабельно отображает вложенные структуры
- удобен для ручного контроля и разбора поведения бота

## Ограничения текущей версии

Несмотря на улучшения, текущая версия всё ещё имеет архитектурные ограничения.

### 1. Одна активная позиция

Сейчас бот торгует только одну позицию одновременно.

Это упрощает контроль, но ограничивает масштабирование и диверсификацию.

### 2. Paper trading, а не live execution

Система пока не выставляет реальные ордера на Binance.

Это хорошо для безопасной разработки, но пока не учитывает полностью:

- реальный `slippage`
- задержки исполнения
- частичные исполнения
- отклонение ордеров биржей
- ограничения по lot size и tick size

### 3. Нет persistent storage

Состояние в основном живёт в памяти процесса.

Это значит, что после рестарта могут потеряться:

- история сделок
- состояние портфеля
- накопленные метрики
- контекст торговой сессии

### 4. Нет полноценного multi-pair runtime

Сейчас бот не торгует несколько символов параллельно.

Он выбирает один активный инструмент и при необходимости переключается на другой.

## Что можно улучшить в будущем

Ниже самые важные направления развития.

### 1. Полноценный `RiskManager`

Нужно вынести риск в отдельный модуль, который будет отвечать за:

- максимальный риск на сделку
- максимальную дневную просадку
- остановку после серии убытков
- ограничение общего риска портфеля
- лимит числа одновременных позиций
- снижение размера позиции после drawdown

### 2. Multi-pair trading

Следующий большой шаг:

- подписываться сразу на несколько символов
- держать отдельное состояние стратегии на каждый символ
- централизованно распределять капитал
- выбирать лучшие сделки из нескольких кандидатов

Это даст:

- больше сделок
- лучшее распределение риска
- меньше зависимости от одной пары

### 3. Реальный backtesting engine

Нужен полноценный движок тестирования на истории:

- replay свечей
- моделирование комиссий
- моделирование проскальзывания
- оценка stop/take/trailing внутри свечи
- расчёт equity curve
- расчёт drawdown
- сравнение разных конфигураций стратегии

### 4. Оптимизация и research pipeline

Для поиска устойчивой стратегии нужно добавить:

- `walk-forward analysis`
- `parameter sweep`
- тесты на устойчивость параметров
- `Monte Carlo` по сделкам
- сравнение по разным режимам рынка

### 5. Улучшение стратегии

Сейчас стратегия уже лучше, чем базовая `EMA/RSI`, но её можно усилить дальше:

- добавить старший таймфрейм как фильтр направления
- использовать `ADX` или другие индикаторы силы тренда
- учитывать структуру объёма
- отделить breakout-режим от mean-reversion режима
- адаптировать параметры под волатильность

### 6. Улучшение market scanner

Сканер можно сделать намного сильнее:

- учитывать не только `24h change`, но и краткосрочную структуру тренда
- анализировать ускорение объёма
- анализировать эффективность движения
- в будущем учитывать spread и order book imbalance

### 7. Постоянное хранилище

Для production-системы желательно хранить:

- сделки
- equity snapshots
- drawdown history
- журнал ошибок
- параметры запуска
- результаты бэктестов

Под это подойдут:

- `PostgreSQL`
- `TimescaleDB`
- либо комбинация `PostgreSQL + Redis`

## Целевая production-архитектура

В зрелом варианте систему лучше разложить на следующие блоки:

- `MarketDataGateway`
- `UniverseScanner`
- `SignalEngine`
- `RiskManager`
- `ExecutionService`
- `PortfolioLedger`
- `BacktestEngine`
- `AnalyticsService`

Тогда бизнес-цепочка станет такой:

1. рынок поставляет данные
2. сигнальный движок генерирует идеи
3. risk manager решает, можно ли открывать сделку
4. execution layer исполняет решение
5. ledger обновляет финансовое состояние
6. analytics сохраняет статистику и метрики

Именно такая структура наиболее близка к production-grade trading system.

## Резюме

Текущая версия бота уже стала заметно сильнее и безопаснее:

- лучше считает деньги
- лучше контролирует риск
- аккуратнее работает со сменой символов
- понятнее логирует своё поведение

Но для следующего уровня зрелости нужно идти в сторону:

- multi-pair runtime
- отдельного risk manager
- persistent ledger
- backtesting и research pipeline
- live execution abstraction

Это и будет путь от хорошего `paper trading prototype` к действительно сильной торговой системе.
